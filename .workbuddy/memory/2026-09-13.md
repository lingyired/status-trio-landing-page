## 三轮修复：电池弧的「幽灵白段」（20:1x）

**现象**：拖电量滑杆时，弧上多出一个白色短段沿圆弧滑向左下。

**根因**（用户先定位的，我复刻数据确认）：缺口是直接编进 `stroke-dasharray` 的，而 **fill 的
dash 段数随电量变化**（实测复刻）：
- battery=100 / gap=64 → `35.3263 29.3474 35.3263 4`（**4 段**）
- battery=86 / gap=64 → `35.3263 29.3474 21.3263 18`（**4 段**）
- battery=60 / gap=64 → `35.3263 68.6737`（2 段，落在缺口内部时退化成一段）
- battery=35 → `35 69`（2 段）
而 `.sti-fill` 上挂着 `transition: stroke-dasharray 260ms ease`。浏览器对**长度不同**的 dash
列表插值时会先把短列表循环补齐（2 段 → `a b a b` 对齐 4 段），于是逐段插值时多出一个可见段。
**注**：`duo-menubar/status-menubar-demo.html` 没有这个 bug —— 它的 `#battery-fill` 只过渡
`stroke` / `opacity`，不过渡 `stroke-dasharray`；是移植成 React 时我给过渡加了 dasharray「为了更顺滑」
才引入的。

**修法**：缺口从 dasharray 里拿掉，改成 **mask 挖洞**。
- `src/status/StatusIcon.tsx`：
  - 新增 `BATTERY_ARC` 常量；删掉 `batteryGapPattern` + `DashPattern`（原来 4 个分支、30 行）。
  - 新增 `batteryGapDash(gapWidth)`（只跟缺口宽度有关，与电量无关）与
    `batteryFillDash(battery)`（恒 `${battery} ${100-battery+4}`，**永远 2 段**）。
  - `<defs>` 里条件渲染 `<mask id={uid-battery-gap maskUnits="userSpaceOnUse" 0 0 120 120>`：
    黑底 rect + **白色虚线**（d = BATTERY_ARC，pathLength=100，stroke-width 8，
    `strokeLinecap="round"`，`strokeDasharray={gapDash}`）。白虚线两端的圆头 = 缺口边缘的圆头，
    外观与旧实现完全一致。
  - 弧线本体包进 `<g mask={showsGap ? url(#…) : undefined}>`，track 变成纯实线
    （不再有 dasharray），fill 用 `batteryFillDash`。**mask 只套弧，不含数字/闪电**，否则缺口会把它们一起抹掉。
- `src/status/status-icon.css`：`.sti-track` 删掉已失效的 `transition: stroke-dasharray`；
  `.sti-fill` 保留该过渡（现在段数恒定，只会等比伸缩）。

**等价性验证**（没开浏览器）：
- 复刻新旧两套算法对账：新 mask dash 与旧 track dash **逐字节相同**
  （gap=64 → `35.3263 29.3474 39.3263`；gap=50 → `38.5362 22.9276 42.5362`）→ 缺口位置/宽度没变。
- 填充弧段数：battery ∈ {0,19,35,60,86,100} × gap ∈ {64,50} 共 12 组，旧实现出现 4 段，
  新实现**全部 2 段**。
- 覆盖范围等价（手工推演）：可见区始终 = [0, firstEnd] ∪ [secondStart, battery]，
  电量落在缺口内时退化为 [0, firstEnd]，与旧的 4 分支逐一对应。
- 产物核对：`index.a5d6e69825.js` 里 `battery-gap` 出现 2 次（定义+引用）、
  `sti-track",d:x` 已无 dasharray、`sti-fill` 的 `strokeDasharray:k`、mask 里
  `strokeLinecap:"round",strokeDasharray`；`100-c+4` 与 `50-t/2` 两个表达式都在；
  旧 4 段分支的痕迹已清（剩下的 `104` 是 1048576 与音量点的 cy:104.2）。
  CSS：`sti-track{stroke:var(--sti-muted)}`、`sti-fill{…transition:…stroke-dasharray .26s…}`。
- `tsc --noEmit` 通过；`pnpm run build` 通过 → 346.2 kB / gzip 162.0 kB。

**通用教训**：给 SVG 上 `transition: stroke-dasharray` 之前，先确认**所有状态下的段数一致**；
段数会变的场合，用 mask/clip 承担「挖洞」职责，别让它进 dash 列表。

## 五轮：换壁纸为 Golden 系列（20:3x）

用户给了两张 6K 图（`~/Pictures/Golden_Dark_6k.png`、`~/Pictures/GoldenGate_6k.png`），
要求压到 1080p + WebP。

### 处理
- 源图 **6016×4147（≈29:20）**，不是 16:9。1080p = 1920×1080，所以走
  **16:9 中心裁切（6016×3384，上下各裁 381px ≈ 9%）→ LANCZOS 缩放到 1920×1080**，
  不做非等比拉伸。
- 文件名去品牌化：`tahoe-dark/light.webp` → **`dark.webp` / `light.webp`**
  （`LandingPage.tsx` 两处 import 同步改；旧文件已删，dist 里无残留）。
  映射：`Golden_Dark_6k.png`（深紫蓝）→ `dark.webp`；`GoldenGate_6k.png`（浅金）→ `light.webp`。
- **编码质量取 q95**（Pillow `method=6`）：实测 PSNR 48.5→49.4 dB、最大误差 14→9，
  体积 42→70 KB。平滑渐变最怕 banding，这点代价值得花。文件 69.7 KB / 78.5 KB。
- 巧合但值得记：**旧 Tahoe 壁纸本来就是 1920×1080**，所以分辨率没有降级，只是换了画面。

### 校验
- `tsc --noEmit` 干净；build 通过 → **440.8 kB / gzip 249.9 kB**
  （原 356.0/165.1；壁纸 71.4+80.4 KB 换掉旧的 29.8+37.2 KB，净增 ≈85 KB）。
- 产物：`static/image/dark.ea322af052.webp` / `light.ff99e5ea29.webp`，JS 里两处引用对得上，
  `grep -rl tahoe dist` 为空。

### 工具坑（跨项目通用）
- **`sips` 不能编码 WebP**：`sips -s format webp` 会打印输出路径但不生成文件（静默失败）。
- **`sips -c H W` 是原生分辨率的中心裁切，不是缩放**：对 6016 宽的图直接 `-c 1080 1920`
  只会截出中间 1920×1080 一块，构图全丢。正确顺序是 `-c` 裁到目标比例 → `--resampleHeightWidth` 缩放。
- 本机没有 `cwebp` / `magick` / `ffmpeg`；可用的是托管 venv 里的 **Pillow 12.3.0（webp: True）**：
  `/Users/lingsmbp/.workbuddy/binaries/python/envs/default/bin/python`。
- 验证脚本留在 **`/tmp/st-wp/make_wallpaper.py`**（含 q82/88/92/95 对比与 PSNR 核算思路）。

## 七轮：首屏性能优化（20:5x）

用户选了「**只做零风险项**」（不换运行时、不上 SSG），毛玻璃按用户选择**先量化再决定**。

### 基线（实测产物，不是估算）
| 资源 | raw | gzip |
|---|---|---|
| `lib-react.js` | 218.2 KB | 68.9 KB |
| `index.js` | 42.4 KB | 15.2 KB |
| `index.css` | 18.9 KB | 4.8 KB |
| `dark/light.webp` | 71.4 / 80.4 KB | — |
| `index.html` | 1.28 KB | 0.68 KB |

诊断出 P0 两条（其余记为待办）：
1. **整页是 CSR 空壳**：`dist/index.html` 只有 `<div id="root">`，首屏 100% 依赖 260 KB JS。
2. **壁纸被 JS 阻塞成二次瀑布**：webp 走 `import` 进 bundle、由 React 渲染 `<img>`（`LandingPage.tsx:74`），
   浏览器要等 JS 下载+执行+渲染完才知道图片地址。而全屏 `object-fit:cover` 的图几乎必然是 LCP 元素
   → LCP 被硬拖到 JS 之后。

### 改动
- **壁纸搬出 bundle**：`git mv src/assets/wallpaper/{dark,light}.webp public/wallpaper/`。
  `src/theme.ts` 新增 `WALLPAPER: Record<ThemePref, string>` 常量表；`LandingPage.tsx` 删掉两个
  `import`（顺带删掉不再需要的 `useMemo`）改查表。
- **`src/index.html` 加内联主题脚本**（vanilla，~20 行，位置在 head 里、早于 Rsbuild 注入的 CSS link）：
  读 localStorage / `prefers-color-scheme` → 写 `data-theme` + `colorScheme` → 注入
  `<link rel=preload as=image fetchpriority=high href=./wallpaper/{pref}.webp>`。
  另加 `<link rel="preconnect" href="https://api.github.com" crossorigin>`。
- **隔离重渲染**：`Hero` / `Features` / `Details` 加 `React.memo`（原全仓 0 处 memo）。
  `Troubleshoot` 在 `Details` 内 → 一起被跳过。
- **滚动**：`onDesktopScroll` 改函数式 updater（`prev === next ? prev : next`），同值走 React bailout。

### 校验（未开浏览器，遵守约定）
- `tsc --noEmit` 干净；`corepack pnpm run build` 通过。
- 产物核对：`dist/wallpaper/{dark,light}.webp` 就位（**构建摘要不列 public 拷贝**，得 `find dist` 才看得到）；
  `dist/static/image/` 已消失、`grep static/image dist JS` 无残留；
  `dist/index.html` 内联脚本在 **L16-36**、preconnect 在 **L38**、Rsbuild 注入的 CSS link 在 **L53**
  → 主题确实早于样式表落定；`grep -o "wallpaper/[a-z]*\.webp" dist JS` 只剩 `WALLPAPER` 表那两条字符串。
- **诚实结论：字节数基本没变**（`index.js` gz 15.2→15.7 KB，react 68.9→68.8 KB）。
  这一轮收益全在**顺序**上 —— 壁纸请求不再挂在 JS 后面、主题不再等 JS 才落定 —— 不在体积上。

### 未做（用户已确认的范围外）
- React 运行时 218 KB（gz 68.8）仍是首屏最大头 → 需要换 Preact 或做构建期预渲染，属 B/C 档。
- `.card` 的 `backdrop-filter: blur(26px)`（`landing.css:233`）与 `.lp-menubar` 的 `blur(22px)`（`:52`）
  **原样保留**，等用户能对比滚动帧率后再定。
- `.pg-hero-icon` 的 `drop-shadow`（`landing.css:477`）+ SVG 内 `feDropShadow`（`StatusIcon.tsx:151`）
  拖滑杆时每帧重光栅化 —— 只加了 memo 减调用次数，滤镜本身**没动**（属视觉，需用户拍板）。
- 壁纸未做响应式多档（单文件 1920×1080，移动端全量下载）；
- `onScroll` 未加 passive / rAF（只做了 bailout）；
- `src/assets/favicon/app-icon-512.png`（38.8 KB）未被任何代码引用，dist 里也没有 —— 死资源，未删。

### 通用教训
- **CSR 站点的资源请求会被 JS 执行顺序绑架**：任何「HTML 里能提前知道地址」的静态资产，
  都不要 `import` 进 bundle —— 放进 `public/` 并用内联脚本/静态标签提前引用，才能和 JS 并行。
- 把主题判定从前端 bundle 挪进 head 内联脚本后，**逻辑就有了两份实现**，必须交叉注释 + 同步改，
  否则会出现「首帧一套、React 一套」的隐性不一致。

### 补记：毛玻璃的最终决定（21:0x）
用户明确表态 **`.card` 的 `backdrop-filter: blur(26px)` 继续保留**，不为了性能降级/去掉。
即上面「未做」里那条待量化项**已结案为「刻意保留」**，后续不要主动改它。
`.lp-menubar` 的 `blur(22px)` 同理（它本来就是要仿真实 macOS 菜单栏）。
→ 相应地，这两处的性能开销被承认为**可接受的视觉成本**。
