## 17:0x ling 反馈「在 X 分享看不到 og 图」→ 根因是 X 缓存，不是配置

**排查路径（服务器侧先全绿）**：robots.txt（子域 404 = 无限制、主域 `Allow: /`）、无 AAAA、

**真因在 nginx access log 里**：

```
199.16.157.182 - - [14/Sep/2026:00:54:19 +0800] "GET / HTTP/1.1" 200 1692 "-" "Twitterbot/1.0"
```

X 的**真爬虫**（`199.16.156.0/22` 是 Twitter 的段）在 **00:54:19 就抓过一次**，那时 og:image

**解法（X 缓存按 URL 走）**：

- 或加 query `https://statustrio.lingai.net/?v=2`；

## 17:4x ling 说「源码里没看到 og 定义」→ 服务端没问题，是看的那份 HTML 是旧的

先核了四个来源（线上子域 / 线上主域子路径 / 本地 `dist` / 本地 `src`），**`og:image` 全在第 66 行，
线上两份 md5 都是 `faab49b1…`** → 服务端没有给旧内容。

再查 access log 把他浏览器那次取件捞出来：

```
163.125.211.197 [14/Sep/2026:17:02:04] "GET /" 200 3041 "…Edg/152.0.0.0…"
```

**3041 B 是 gzip 后的当前版本**（我刚实测 3029 B，同量级），而旧版是 **1692 B** ——
**他浏览器拿到的确实是含 og:image 的新版**。服务端这条线索排除。

**两个真正的原因**（都属"看的方式"，不是站点问题）：
1. **`view-source:` 标签页是静态快照，不会跟着刷新**。那个 tab 若是早先打开的（哪怕只早几分钟），
   内容就停在打开那一刻 —— 这是最可能的。
2. **搜错词**：中文「og 图」只出现在**第 52–64 行的注释**里（讲这张图的设计理由），
   真正的 meta 是英文 `og:image`（第 66 行起）。搜中文 → 只命中注释，看着就像"只有说明没有实现"。

**顺带挖出一个真隐患 —— 17:51 ling 一句「好」= 批准，已修（2026-09-14 17:5x）**：
nginx 对 HTML **不发 `Cache-Control`**，只有 `ETag` / `Last-Modified`。
按 RFC 启发式缓存，新鲜期 = `(Date − Last-Modified) × 10%` ——
**站点若一周没更新，浏览器可最长约 17 小时不回源**，下次部署后老访客可能迟迟看不到新壳子。

已给**三个 vhost 里所有伺服 HTML 的 `location`** 各加 `add_header Cache-Control "no-cache";`
（本项目的 `statustrio.lingai.net.conf` 的 `location /`，以及 `lingai.net.conf` 的 `/statustrio/`）。
备份 `*.bak.20260914175217`，`nginx -t` 通过后 `systemctl reload nginx`。

- **`add_header` 不继承**：`^~ /static/` 自带 `add_header` → 天然仍是 1y immutable，无需隔离。
- 实测两入口 HTML 均 `no-cache`；静态资源仍 `max-age=31536000 + public, immutable`；
  304 生效（ETag `"6aa7b793-16ce"` → 304）；HTML md5 仍 `faab49b1…`、`og:image` ×4 未受影响。
- 本项目产物里的 `og.jpg` / `wallpaper/*.webp` 现在也是 `no-cache`（**好事**：换图立刻生效，
  以前要 query 破缓存）。
- 详见服务器侧文档 `lingai-server/.workbuddy/VPS_ACCESS.md` **§15**。

> ⚠️ 验证手法坑：本机 `awk` 是 **mawk，不支持 `IGNORECASE`**。用它写 `/^cache-control:/`
> 会静默返回空 → 误判"头没生效"。验响应头一律 `curl -sI | grep -i`。
